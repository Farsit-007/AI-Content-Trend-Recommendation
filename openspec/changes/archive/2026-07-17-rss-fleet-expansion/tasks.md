## 3. Verification

- [x] 3.1 `cd backend && npm test && npm run build`
- [x] 3.2 Manual ingest against live Atlas/Redis with the 21-feed list → new labels appeared: `rss:thenewstack.io` (26 fetched), `rss:smashingmagazine.com` (40), `rss:stackoverflow.blog` (40), `rss:blog.cloudflare.com` (20), `rss:changelog.com` (50), `rss:technologyreview.com` (10), `rss:github.com` (50, all 5 release feeds merged under one label as designed), `rss:export.arxiv.org` (25). Spot-checked stored items: a `rss:github.com` item (`v16.3.0-canary.87`) and an `rss:export.arxiv.org` item both have real `published_at` values from their feed entries. **Note**: `rss:feed.infoq.com` never appeared — that one feed errored on this run (logged: `RSS feed https://feed.infoq.com/ failed`) and, per the adapter's existing per-feed-failure design, a feed that produces zero items doesn't get its own summary row (only feeds that yield ≥1 item generate a label) — this is pre-existing adapter behavior, not a regression, but means a permanently-broken feed is invisible in the summary rather than showing `fetched: 0`. Not a blocker for this change; worth knowing.
- [x] 3.3 **Guardrail exceeded, flagging honestly rather than rubber-stamping**: total per-run fetched volume was 619 (RSS: 411 across 14 successful labels + hackernews 63 + devto 66 + github_trending 42 + lobsters 25 + mastodon 12), well over the parent plan's ~400-item target. The plan's guardrail was set assuming Tier-1+2 sources' original caps; it wasn't re-evaluated after the already-shipped `lobsters-adapter`/`mastodon-trending-adapter` changes added their own volume on top of this RSS expansion. This is a real cost signal (more embedding calls + LLM categorization batches per run), not a bug in this change specifically — recommend a follow-up look at trimming RSS per-feed volume (e.g., some feeds like `wired.com`/`changelog.com` returned their full 50-item cap) if this run-rate holds, per the parent plan's own stated escalation path ("if post-ship run history shows per-run embedding volume doubling, trim caps before adding the next source").
- [x] 3.4 Did not simulate a live hung feed (no practical way to stand up a slow-responding endpoint in this environment). Verified instead via `rss-parser`'s own source (`node_modules/rss-parser/lib/parser.js`): the library applies `this.options.timeout` via a real `setTimeout`/reject in its request path, and the unit test (1.3) confirms the adapter's `Parser` is constructed with `{ timeout: 10_000 }`. **Correction to the proposal's framing**: the library was not actually hang-forever before this change — it already defaulted to a 60-second internal timeout (`DEFAULT_TIMEOUT = 60000`) when none is passed. This change tightens that from 60s to 10s; it's a real improvement to the worst-case stall (and makes the timeout an explicit, intentional value instead of an implicit library default) but the original "one hung feed stalls the run indefinitely" claim in the proposal/design overstated the prior behavior.
